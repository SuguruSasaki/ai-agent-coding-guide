# Adopted Google Rust Style Guide rules

Source: [Google Rust Style Guide](https://google.github.io/styleguide/rustguide.html), checked on 2026-10-24. This is a summary. Consult the original exceptions and codebase-specific scope when applying a rule. `[G-...]` IDs identify sources in review findings. `MUST`, `SHOULD`, and `REVIEW` are this skill's operational categories.

| Area and ID | Category | Decision and purpose | Original section |
| --- | --- | --- | --- |
| Naming `G-N1` | SHOULD | Match `as_`, `to_`, and `into_` names to their ownership behavior. Use names such as `new` and fallible `try_new` to show construction semantics. Avoid abbreviations unfamiliar to new readers. | Naming methods; Naming initialization functions; Avoid abbreviations |
| Naming `G-N2` | REVIEW | Give type lifetimes names that explain their roles. The guide permits anonymous lifetimes and short names for simple local relationships. | Naming lifetimes; Naming generic parameters |
| Formatting `G-F1` | MUST | Check formatting with the project's rustfmt. Use `rustfmt::skip` only for cases the guide permits, such as generated code or alignment that improves readability. | Follow public Rust style rules; Use the appropriate formatting tool; Opting out of automatic formatting |
| Ownership `G-O1` | REVIEW | Consider borrowing and unique ownership before `clone`, `Rc`, or `Arc`. Copies or shared ownership may still be reasonable when lifetimes or task boundaries would otherwise become too complex. | Avoid `Rc` and `Arc`; Prefer borrows over deep copies |
| API `G-A1` | SHOULD | For borrowed, read-only inputs, prefer flexible references such as `&str` over `&String` and `&[T]` over `&Vec<T>`. Do not apply this rule to a parameter whose ownership is needed for storage. | Accept flexible references for immutable data |
| API `G-A2` | REVIEW | Consider an enum when a boolean argument's meaning is unclear at a call site. A boolean can be appropriate when a field name or local context makes its meaning clear. | Prefer `enum` over `bool` in APIs |
| API `G-A3` | REVIEW | Consider iterator inputs and outputs for reusable libraries. In application code, the simplicity of `Vec` or slices may be more useful. Balance `Into<T>` call-site convenience against generic complexity. | Iterators vs. owned collections in return types; Iterators vs. slices in function parameters; Accepting `Into` |
| API `G-A4` | REVIEW | Consider `#[non_exhaustive]` for public enums and structs with public fields used across team boundaries. Check its construction cost and exceptions for stable types. | Apply `#[non_exhaustive]` to publicly-exposed enums; Apply `#[non_exhaustive]` to public structs with public fields |
| Errors `G-E1` | REVIEW | Use `Option` when no additional failure detail is useful, `Result` when callers need a reason to recover, and panic for bugs or violated invariants. | Reporting errors |
| Errors `G-E2` | SHOULD | Express checked presence with matching instead of checking then calling `unwrap`. If panic is necessary, prefer `expect` with a reason. | Prefer pattern matching over check-then-unwrap; Prefer `expect` over `unwrap` |
| Types `G-T1` | REVIEW | Consider a newtype for distinct meanings, easily confused values, or a dedicated API. Prefer named fields when tuple positions obscure meaning. | Newtypes versus type aliases; Prefer named fields over tuples and non-newtype tuple structs |
| Traits `G-T2` | SHOULD | Implement a standard trait when its contract fits, and derive implementations that need no custom behavior. Define traits for a concrete need rather than merely organizing code. | Implement known standard library traits instead of custom methods; Use `#[derive()]` if possible; When to define a trait versus an inherent implementation |
| Concurrency `G-C1` | MUST | Do not reach into a poisoned mutex and continue using its contents; the protected state may be inconsistent. | Handling poison |
| Documentation `G-D1` | SHOULD | Document public API contracts, input-dependent panic conditions, and unsafe invariants. Omit comments that only repeat an obvious name. | When and how to write documentation |
| Safety `G-S1` | MUST | Do not add unsafe code if safe Rust can provide the same behavior. Isolate necessary unsafe code behind a safe abstraction, explain it in a `SAFETY:` comment, and document its technical justification. | Unsafe code |
| Testing `G-X1` | SHOULD | Use the test framework appropriate to the codebase. Give assertions useful failure context and verify changed contracts. | Use the right per-codebase test framework; Use context strings to clarify assertions |
| Readability `G-R1` | SHOULD | Split long iterator chains into named intermediate values or loops when clearer. Keep concise operations such as `any` when they directly express the intent. | Don’t use iterator combinator chains when direct iteration is clearer |

Google treats library API design guidance more strictly and favors direct, simple implementation in application code. Its import guidance generally avoids glob imports while permitting exceptions such as `use super::*`. Many rules require an examination of actual usage and cannot be decided by formatting tools alone.
