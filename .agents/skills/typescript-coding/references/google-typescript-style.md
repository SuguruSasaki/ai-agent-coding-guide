# Google TypeScript Style Guide: working summary

Primary source: [Google TypeScript Style Guide](https://google.github.io/styleguide/tsguide.html). This is a selective summary. The public guide says its internal-Google origins may make some advice unsuitable for external projects. Its examples are non-normative: do not invent rules from incidental formatting in them. Consult the linked sections for details and exceptions.

`MUST`, `SHOULD`, and `REVIEW` are operational categories for this skill, not the guide's RFC 2119 terms or finding severity.

| ID | Level | Area | Working rule and reason |
| --- | --- | --- | --- |
| G-T01 | MUST | Source and modules | Use UTF-8 source, ES module imports/exports, and modules rather than TypeScript namespaces or `require`; namespaces have a third-party interop exception. [Source](https://google.github.io/styleguide/tsguide.html#source-file-basics) [Modules](https://google.github.io/styleguide/tsguide.html#use-modules-not-namespaces) |
| G-T02 | SHOULD | Imports and exports | Prefer named imports when they improve local clarity; namespace imports can help with large APIs. Use named exports, minimize exported surface, and avoid mutable exports. Default imports of external code are permitted when required. [Source](https://google.github.io/styleguide/tsguide.html#imports) [Exports](https://google.github.io/styleguide/tsguide.html#exports) |
| G-T03 | MUST | Variables and control flow | Use `const` unless reassignment is needed, then `let`; never `var`. Use `===`/`!==`, except `== null` or `!= null` when checking both nullish values intentionally. [Source](https://google.github.io/styleguide/tsguide.html#local-variable-declarations) [Equality](https://google.github.io/styleguide/tsguide.html#equality-checks) |
| G-T04 | SHOULD | Formatting | Preserve the guide's source-file ordering, ordinary single-quoted strings, and function/comment formatting. Follow the target project's formatter where its external-project policy documents a difference. The guide does not impose a general column limit from its examples. [Source](https://google.github.io/styleguide/tsguide.html#source-file-structure) [Strings](https://google.github.io/styleguide/tsguide.html#string-literals) |
| G-T05 | MUST | Naming | Use the guide's casing by identifier kind and avoid type-encoding name decorations such as `IFoo`, `opt_`, or private `_` prefixes. Account for stated framework conventions. [Source](https://google.github.io/styleguide/tsguide.html#naming) |
| G-T06 | REVIEW | Public API | Keep exports minimal; inspect call sites for meaningful names, clear parameters, and types that express valid states. Consider an options object when positional Boolean arguments obscure intent. [Source](https://google.github.io/styleguide/tsguide.html#export-visibility) [Call comments](https://google.github.io/styleguide/tsguide.html#comments-when-calling-a-function) |
| G-T07 | SHOULD | Types | Prefer `interface` for object shapes, specific types or `unknown` over `any`, and the simplest type construct that expresses the contract. Use type inference for trivial expressions; annotate complex or public return types when they clarify behavior. [Source](https://google.github.io/styleguide/tsguide.html#prefer-interfaces-over-type-literal-aliases) [Inference](https://google.github.io/styleguide/tsguide.html#type-inference) [Mapped types](https://google.github.io/styleguide/tsguide.html#mapped-and-conditional-types) |
| G-T08 | SHOULD | Nullability and assertions | Keep absence visible near its source. Avoid unsafe `as` and non-null `!` assertions without an obvious or explained invariant; prefer narrowing/runtime checks. If an assertion is necessary, use `as`, not angle-bracket syntax. [Source](https://google.github.io/styleguide/tsguide.html#undefined-and-null) [Assertions](https://google.github.io/styleguide/tsguide.html#type-and-non-nullability-assertions) |
| G-T09 | MUST | Errors | Instantiate exceptions with `new`, throw/reject only `Error` objects, and avoid silent empty catches. Prefer exceptions to ad-hoc error containers for exceptional cases; document a known non-`Error` throwing external API when handling it. [Source](https://google.github.io/styleguide/tsguide.html#exception-handling) |
| G-T10 | SHOULD | Documentation | Use JSDoc for users of an API and `//` for implementation notes. Document top-level exports and non-obvious members with information beyond their names and types; avoid redundant JSDoc type declarations. [Source](https://google.github.io/styleguide/tsguide.html#comments-and-documentation) |
| G-T11 | MUST | Toolchain | Type-check TypeScript files with the project's standard toolchain. Do not silence compiler errors with `@ts-ignore` or `@ts-nocheck`; `@ts-expect-error` has a narrow, discouraged allowance in unit tests. [Source](https://google.github.io/styleguide/tsguide.html#toolchain-requirements) |
| G-T12 | REVIEW | Changes and tests | Keep unrelated style churn out of focused changes. Test annotations, partial mocks, and generated code have documented exceptions; check whether they are truly applicable before flagging them. [Source](https://google.github.io/styleguide/tsguide.html#policies) [Toolchain](https://google.github.io/styleguide/tsguide.html#toolchain-requirements) |

Automated checks can identify syntax and configured lint violations. They cannot determine whether a Boolean obscures a domain state, an asserted tool response is actually validated, a promise outlives its owner, or an error contains enough context. Those require review of requirements and callers.
